# Per-configuration audit checkpoints

Base: `2e44e963`. With `--checkpoint-dir`, each planned source translation unit and compile configuration now produces one complete ten-section `.qo` as its worker finishes. The full unit key is hashed into the filename, so two compile commands for one C file remain separate. Every file repeats the run plan and global inputs; the existing binary schema and refutation-table identity stay intact. Worker-side atomic write, file sync, rename and directory sync happen before ordered publication. The consumer then prints unit output in plan order and the composer rejects missing, duplicate, corrupt or mixed-run files before writing the report. An interrupted run retains completed units for `--resume`; an unfinished `.qo.partial` is ignored.

The per-unit split is behavioral orchestration, not an analyzer change. `proof/QCore/Checkpoints.lean` now states the singleton-partition resume/compose theorem and `proof/AuditCheckpoints.lean` registers it. The proof assumes the Rust fingerprint captures every analysis input, as the existing checkpoint proof did. It does not prove SHA-256 collision resistance or filesystem crash consistency.

Focused end-to-end fixture evidence: four tests passed on the initial implementation (`cargo test -p qcore-audit --test checkpoint_cli --no-fail-fast`, exit 0; 4 passed, 0 failed, 63.44 s), covering whole-run report bytes at jobs 1 and 4, reuse, one changed unit, tampering repair, missing/duplicate/mixed/truncated composition, text round trip, selection with an absent compile record, and two distinct configurations of one source. A separate process-interruption test passed (`cargo test -p qcore-audit --test checkpoint_cli interrupted_run_preserves_completed_units_for_resume -- --exact`, exit 0; 1 passed), killing the run after a sealed unit and checking that resume reused completed work, recomputed missing work and reproduced whole-run report bytes. These are fixture observations, not corpus coverage claims. Full standing-gate evidence follows after integration with the independent prepare-path change.

Memory bound: at most `--jobs` unit analyses and their individual checkpoint encodings are live; ordered consumption keeps only small completion records. A slow early unit cannot prevent later completed workers from sealing files, though the report waits for all planned units. Repeating the complete plan/global sections in each `.qo` uses more disk than the former per-library layout. No new opt-in flag is needed beyond `--checkpoint-dir`.

Follow-on already registered elsewhere: two-phase resume still overwrites first-phase checkpoints with second-phase files under the same names (`CHECKPOINT-TWO-PHASE-RESUME-NEVER-REUSES`); this card preserves the refutation-table digest boundary and does not change that behavior.
