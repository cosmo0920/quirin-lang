## 1. The census

**Question.** Under user decision U2 (2026-10-14: "List it in every dependent
verdict"), a declaration names `rk_no_plugin_library` when its body may run an
rk_conf callback: the log callback `rd_kafka_log_buf` calls
(`rdkafka.c:280-305`, through `rd_kafka_dbg` / `rd_kafka_log` /
`rd_kafka_log0`), any other function-pointer member of `struct
rd_kafka_conf_s`, or an interceptor method (`method->u.on_*`, registered only
by a plugin's `conf_init` or the application). Only under the premise are
those sets closed over the run's registrations.

**Method** ([`scripts/census.sh`](scripts/census.sh)). Every librdkafka C unit
of the pinned production compile database (94) was preprocessed with its own
recorded command at both audited revisions
([`preprocess.py`](scripts/preprocess.py); all exits 0), so every macro is
expanded. [`reach.py`](scripts/reach.py) builds an over-approximating call
graph from the preprocessed text and walks it from each declaration:

* every call of a name librdkafka defines is an edge (same-named statics are
  merged);
* a member call is an rk_conf sink (`log_cb`, `error_cb`, … — the
  OP-APP-RK census list, `scram_H` excepted: no property writes it), an
  interceptor sink (`u.on_*`), or an unresolved indirect call;
* a call of any other name, of an expression, or of an external that calls
  back (`qsort`, `bsearch`, `thrd_create`, …) is an unresolved indirect call;
* `rd_kafka_crash` with a null `rk` reaches nothing (it prints and aborts,
  `rdkafka.c:6640-6649`); with any other `rk` it reaches `rd_kafka_dump0`.

A declaration is **`rk-conf`** when a path reaches a sink, **`indirect`**
when only an unresolved indirect call is reached (given the premise: the
conservative label), and **`none`** otherwise. Within the 80, eleven
indirect calls of ten declarations were resolved by reading the bodies; each
resolution and its source lines are in `RESOLVED` and in
[`artifacts/census.json`](artifacts/census.json). Five of those declarations
state the callback clause themselves
(`resource_callback_registry_invoked` on `rd_list_destroy`, `rd_list_clear`,
`pb_write`, `pb_encode_varint`; `resource_callback_invoked` on
`rd_kafka_topic_partition_list_sort`): those calls are decided at each call
site over the candidates' own declarations, which publish their own premises
(rules 13u, 13w), so the invoker's body is read without them.

**Both revisions.** All 253 declarations of the ten librdkafka modules have
identical definitions (preprocessed text, tree roots normalised) and identical
census results at `66910c10` and `046accf6`.

## 3. The null views

The 86 `null_deref.qv` declarations are bounds-contract-v1 views. The format
**cannot carry a premise**: the bounds clause parser accepts only its own
vocabulary and rejects any other clause (`unsupported bounds clause`,
`crates/qcore-contract/src/bounds_contract.rs:960`), and a null-deref view
beside a resource view may state only the selector and the null clauses
(`check_null_deref_only`, `crates/qcore-contract/src/contract_views.rs:874-905`).
A null row's dependency fields carry only `null_premises`
(`null-deref:FUNCTION:LINE:VARIABLE`, rule 14n). Per the brief, no syntax is
invented: this is a decision for the user (section 4). For the record, the
census over the views' bodies: 75 `rk-conf`, 2 `indirect`
(`rd_kafka_sasl_broker_init` / `_term`, the SASL provider's method table), 9
`none`.

## 5. Prediction

* **Verdicts.** Corpus 936 / 9 / 3,889, system 93 / 4 / 351, slice 52 / 1 /
  347 / 4 Pending, and the null property (corpus 1,113 / 1,435 / 2,355 / 18
  Unsafe; system 84 / 125 / 245; slice 71 / 103 / 232) are identical: a named
  premise changes no mode (C04.18; rule 13u). Every row's status and leaves are
  identical, and so is every row's `contract_dependencies` field, since the
  row field names declarations and the premise is a declaration's.
* **Sidecar.** The 34 declarations' records gain `rk_no_plugin_library` among
  their premises. A named premise is a clause no evidence covers (rule 13j), so
  any of the 34 that is `validated` becomes `partly-validated`, with the
  premise among its `uncovered_clauses`; the roll-up's buckets may move
  accordingly (counted in section 6).
* **Pins.** The 34 rows of `EXPECTED_CONTRACTS` gain one clause each; the
  resource-v1 and retaining declaration counts (455, 78) do not move. The
  lock re-pins the 34 at both revisions.
* **Rows.** Every Safe or Pending row whose `contract_dependencies` names one
  of the 34 lists the premise afterwards; those that did not list it before
  are the point of the card. Section 6 lists them from the BEFORE run.
