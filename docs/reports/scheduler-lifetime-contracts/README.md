The pinned Monkey scheduler now has an explicit, report-owned decomposition of
cleanup, HTTP thread destruction, creation and purge, plus a checked finite
cleanup consumer. These are proposed contracts with **Open C-source truth**.
They add no production declaration, provider pin, graph atom, safety verdict or
contract standing. The scheduler's measured priority remains blocked; score 2
is a conditional planning rank and promises no two safety gains.

The actual source path is `sched_thread_cleanup` (scheduler.c:614–632) to
`mk_http_thread_destroy` (http_thread.c:251–272), then inline
`mk_thread_destroy` (thread_libco.h:64–78). Destruction conditionally frees the
current thread's libco params and clears **that** TLS slot, unlinks the HTTP
node, resets the borrowed session/channel/event type, invokes optional
`cb_destroy` on the embedded data, deletes the coroutine, then frees the
parent allocation. The HTTP object is embedded in its parent allocation;
borrowed session, request, channel, event and handler data are not owners to
free. Safe iteration saves a successor before destruction; a callback that
releases or mutates that successor breaks the premise even if it preserves its
own parent. The complete selected and other list footprints are protected.

The Rust consumer checks exact ordered effects against a finite state:
32 threads, 512 live allocation tokens, 64 effects per callback and 2,560 trace
steps. It checks worker identity, exact disjoint membership, suspended
coroutines, parent/callee ownership, borrowed lifetimes, parent-role current TLS and params-TLS separation.
A callback may read live resources and write/release its separately owned
resources; it cannot invalidate any parent, coroutine, borrowed chain, params
or saved successor. Missing, reordered, extra or mismatched effects refuse.
Refusal leaves the input model untouched. This is a checker refusal, **not a C
rollback path**: the actual destroy function returns zero after effects and has
no guarded failure/unchanged branch. Its result type carries no Safe verdict
or standing, and no production analysis caller reads it.

Creation and failure paths remain concrete and distinct:

- Missing scheduler and parent-allocation failure return before new ownership.
- The explicit embedded-data NULL branch returns after allocation without a
  source free. Its feasibility under valid layout is unestablished; no leak or
  unreachable-path claim is made.
- `co_create` is unchecked after insertion and request-alias assignment. A NULL
  result proceeds to parameter setup/context switching; no unchanged-failure or
  successful-created postcondition follows.
- `thread_get_libco_params` logs allocation failure and still stores/returns its
  result; consumers later dereference it. Allocation/TLS success stays Open.
- The library callback dispatches `handler->cb(request, handler->data)`;
  event-add failure is ignored, request-end failure chooses close=true and
  success chooses false, then purge/yield follows. The plugin branch is FIXME.
  Callback/transitive effect closure and every dependent object lifetime remain
  separate; no neutral, consumed or acyclic premise is invented.
- Purge returns −1 on missing scheduler before changing close or lists;
  otherwise it assigns close and moves the node from active to purge.
- Cleanup handles empty/nonempty lists; destruction retains all four positive
  params-present/absent and callback-present/absent combinations.

The following prerequisites remain Open and block production discharge:
`SCHEDULER-TLS-RETIREMENT` (mk_thread TLS is set by resume but never cleared by
destroy; the bounded consumer refuses its retiring alias),
`SCHEDULER-EXTERNAL-ALIAS-RETIREMENT` (request->thread/channel.thread and other
aliases cannot be used after free), `SCHEDULER-CALLBACK-EFFECT-CLOSURE`
(returning compatible candidates and transitive effects),
`SCHEDULER-LIST-EMBEDDING-TRANSPORT` (actual C circular-list membership, object
layout and no concurrent/reentrant writer), and
`SCHEDULER-CREATE-TLS-LIBCO-FAILURES` (TLS API results, initialization, allocation,
unstarted/plugin/failure paths). Creation/purge/dispatch currently have readable
propositions, **not executable source-to-effect consumers**. A future production
bridge must discharge those leaves through checked extraction/consumers and
explicit pin updates; the current model does not silently support them.

Integration correction: the initial finite API accepted any live token in
`current_thread`, while its retirement check only excluded selected parent
keys. A presented callee token or params token could therefore survive as stale
TLS after that resource was freed. This was a model admission defect, with no
production caller or C-source safety claim. Patch `1b315995a` requires this TLS
slot to be absent or name a live parent key in the modeled thread map, and still
forbids retiring that parent. A live unselected parent is preserved through
cleanup. With an empty selected list, a valid current parent and nonnull params
both remain unchanged; a callee/params token in current-thread TLS still refuses
because its role is malformed, even though that empty operation frees nothing.
The matching Lean admission premise requires an explicit parent witness, with
`non_parent_current_tls_forbids_admission`. This is a finite model role
restriction, not a new claim about C TLS behavior or a global alias proof.
