# Landing repair: provider workspace lock (2026-11-01)

The RULE32A-PILOT landing (`62da8997d`) made `rule-32a-caller-frame-hold` a
dependency of `qcore-c-gateway`. The root `Cargo.lock` was regenerated, but
`providers/Cargo.lock` was not, even though the provider workspace builds
`qcore-c-gateway` too. The RULE32A landing gate
(`gate_scope.py --base c82895503`) chose "provider gate: no", so no provider
build ran. As a result, every `--locked` provider build on `62da8997d` and
`eb49bb6ce` refuses with "cannot update the lock file": `contracts.py sync`,
`package.py build` / `reproduce` and the provider suite.

Found by the PACKAGE-BYTES-DEPEND-ON-CHECKOUT landing's targeted check:
`package.py reproduce` exited 1 at `cargo metadata --locked`.

## Repair
`b2b10e54d` adds the missing 8 lines (the `rule-32a-caller-frame-hold`
package and its edge from `qcore-c-gateway`) to `providers/Cargo.lock`,
generated by `cargo metadata --offline` with no other change.

## Gate
`python3 scripts/gate_scope.py --base eb49bb6ce` on the landing tip
(PACKAGE-BYTES records `91211e9d0` plus `b2b10e54d`) chose "provider gate:
yes" and ran 13 steps, all exit 0. Results: Rust 8,970 passed / 0 failed / 15
ignored over 587 units; Python 577; package build and verify of all five;
provider tests 133 / 0 / 1; provider fmt and Clippy. Afterwards
`providers/package.py reproduce` exited 0 (112 files identical). Record:
[gate.json](gate.json).

## Why the gate missed it
`gate_scope.py` selects the provider gate from paths under `providers/` and
string-literal readers. A change to the dependency set of a root crate that
the provider workspace builds by path (`crates/qcore-c-gateway/Cargo.toml`,
root `Cargo.lock`) reached neither. Registered as GATE-SCOPE-PROVIDER-LOCK.
