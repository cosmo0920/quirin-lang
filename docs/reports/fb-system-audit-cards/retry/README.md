## Observed lifetime route

A task claims a reusable map id and begins with `users=0` ([`src/flb_task.c:445-473`](https://github.com/fluent/fluent-bit/blob/864c3d97f3589515285a19396ed8dfc85cda08ae/src/flb_task.c#L445-L473)). On a `FLB_RETRY` completion, the engine creates or reuses the per-output retry, decrements the active flush user without reaping the task, and asks the scheduler to carry the retry pointer ([`src/flb_engine.c:729-803`](https://github.com/fluent/fluent-bit/blob/864c3d97f3589515285a19396ed8dfc85cda08ae/src/flb_engine.c#L729-L803)). A successful completion releases that route, clears its retry and decrements with release checking (`src/flb_engine.c:680-687`). The scheduler owns a request and timer while pending, including its long-wait list; invalidation searches both lists by the retry pointer (`src/flb_scheduler.c:268-325,354-387`). Its callback dispatches first and destroys the request on a zero return (`src/flb_scheduler.c:593-605`). When dispatch fails after destroying the retry, invalidation also destroys the request; the handler's nonzero return avoids a second destroy. This is a relevant guard against treating the lexical order as a double free.

Retry dispatch raises and flushes the input chunk before starting another output flush. An unavailable chunk or read reschedules; a scheduling failure destroys the retry and destroys the task only when no users or retries remain (`src/flb_engine_dispatch.c:95-175`, `src/flb_task.c:291-315`). For synchronous output, a queued task gets a temporary user before queue insertion; moving it to flush removes that user, and a successful flush adds its own (`src/flb_output.c:280-382,415-463`). Task destruction clears the map, output routes, chunk and retries (`src/flb_task.c:899-947`). Shutdown exits output instances before destroying input instances and their tasks (`src/flb_engine.c:1629-1650`, `src/flb_input.c:1230-1231`); scheduler teardown follows from config destruction (`src/flb_config.c:684-686`). This source order alone does not prove or disprove callback overlap with teardown.

## Concrete candidates and controls

**C1 — timer retained on retry-request allocation failure.** `flb_sched_request_create` allocates and links a timer at `src/flb_scheduler.c:275-280`; if subsequent request allocation fails at `:282-285`, it returns without destroying that timer. The analogous `flb_sched_retry_now` branch explicitly destroys it at `:965-970`. Scheduler teardown eventually destroys linked timers (`:827-852`), so the supported claim is retention during the running process after a recoverable failure, not a demonstrated permanent leak. A stubbed isolated harness now forces failure of only the second allocation and observes one live timer *before* simulated teardown; this supports the retention branch but does not exercise the full Fluent Bit scheduler. A production fault-injection run would check the real timer list before teardown.

**C2 — synchronous queue allocation leaves a temporary task user.** `flb_output_task_singleplex_enqueue` increments `task->users` at `src/flb_output.c:360-368`; if `flb_task_enqueued` allocation fails, the callee destroys `retry` when present and returns `-1` (`:288-295`), while the caller returns at `:370-374` without decrementing. The ordinary queue-flush decrement at `:325-329` is unreachable on this arm. Input teardown ultimately destroys tasks despite the count, so the bounded consequence is a task/chunk retained until teardown. Inject this allocation failure in one-route first-dispatch and retry cases, checking the user count and map before shutdown. The retry caller at `src/flb_engine_dispatch.c:157-167` trusts enqueue to own failure cleanup.

**C3 — possible orphan after a queued retry's flush fails.** `flb_output_task_queue_flush_one` removes the temporary user without release checking, then destroys a retry on flush failure (`src/flb_output.c:325-341`). `flb_output_task_flush` can fail before adding a new user, or after rolling it back (`:415-463`). A one-route retry with no other user/retry may therefore remain mapped with `users=0` after the retry is destroyed. Other active routes or retries are contrary guards; a zero-user task is reaped by `flb_task_users_release` only when called (`include/fluent-bit/flb_task.h:171-193`). Reproduce with a queued retry behind a synchronous flush, fail flush creation or pipe write, and inspect map/input task list after the first flush finishes.

**C4 — stale completion identity, hypothesis only.** The completion key carries task id and output id, without a generation (`include/fluent-bit/flb_task.h:47-52`); the engine dereferences the current task-map entry (`src/flb_engine.c:579-608`), and ids are reusable (`src/flb_task.c:42-77`). Normal outstanding users can keep old tasks alive until completion, and event-loop/shutdown ordering may prevent a stale queued event. No reachable duplicate or stale completion was established. A reproduction must first prove the event can remain queued through task destruction and id reuse, then observe its actual handler path. The absence of a generation field alone is not an upstream defect finding.

The strongest next step is fault injection for C1 and C2. C3 needs queue-state setup. C4 needs an executable timing witness before any defect claim. The separate semantic card still needs the selected route's accepted-retirement and refused stale/duplicate controls, Lean parity, and production import validation.
